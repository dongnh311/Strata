# q2_0 against Gyro-S on an RTX 3060 (2026-10-28)

This compares the q2_0 model this PC already served with Gyro-S, for speed, coding
ability and a 256K long-context check. Gyro-S was removed after the run.

## Machine and build

- RTX 3060 12 GB, compute capability 8.6; Intel i7-14700K, 28 threads; Windows.
- Engine `0.1.52` (`D:\GitHub\Strata-data\build-v026\strata.exe`), CUDA 13, sm_86.
- Both models used the same flags: 32K context for the paired tests, `kv q4_0`,
  `kv-resident 32768`, `spec 4`, `spec-min-p 0.7`, the same MTP draft, `expert-cache auto`,
  `prefill auto`, no vision and no control vector.
- q2_0: the ISTA-DASLab Q2_0 pack. Gyro-S: `Qwen3.8-Flash-Next-Gyro-S-TQ1_0.gguf`,
  58,487,015,808 bytes, SHA-256 `c6ea1b08ca312f99095b27588ba35976b53f948268e7f91e7761926aa01d9c87`
  (the hash in `setup.py`), and a pack made with `tools/iq_pack.py --compat-bf16`.
- The engine loaded 31.64 GiB for q2_0 and 24.02 GiB for Gyro-S.
- Device under test: one model at a time. The q2_0 numbers below are from the same
  32K lab settings as Gyro-S, not from the 262K serving profile.

## Speed

One warm-up and three measured requests for each prompt length, temperature 0,
`max_tokens 256`; the table gives medians of the engine's own `timings`.

| Prompt | q2_0 prefill | Gyro-S prefill | q2_0 decode | Gyro-S decode |
| --- | ---: | ---: | ---: | ---: |
| about 78 tokens | 116.3 tok/s | 144.1 tok/s | 73.3 tok/s | 63.4 tok/s |
| about 883 tokens | 545.8 tok/s | 599.7 tok/s | 89.5 tok/s | 68.8 tok/s |
| about 2,500 tokens | 839.2 tok/s | 778.0 tok/s | 86.9 tok/s | 64.6 tok/s |

Gyro-S decoded 13.5%, 23.1% and 25.7% slower at the three lengths. Its prefill was
faster on the two shorter prompts (+23.9% and +9.9%) and 7.3% slower at 2,500 tokens.
A second Gyro-S run with `--spec-min-p 0.5` was not faster (63.0 / 63.2 / 62.7 tok/s).

## Coding

60 of the 164 HumanEval tasks, spread evenly over the ids, one sample per task,
temperature 0, `max_tokens 4096`, the same test files for both models. A task counts
only when every assertion in its official test passes.

| Model | Passed | Score | Time for 60 tasks | Median per task |
| --- | ---: | ---: | ---: | ---: |
| q2_0 | 53/60 | 88.3% | 565 s | 5.1 s |
| Gyro-S | 54/60 | 90.0% | 946 s | 9.2 s |

The one-task difference is not a clear capability difference. Both passed 51 tasks;
q2_0 passed two that Gyro-S failed, Gyro-S passed three that q2_0 failed. q2_0 was
about 1.7x faster over the set and 1.8x faster per task. Both failed
`HumanEval/50`, `/86`, `/99` and `/146`; q2_0 also failed `/39`, `/77` and `/116`;
Gyro-S also failed `/47` and `/97`.

A separate ten-task suite (intervals, duration parsing, an LRU cache, DP, a rotated
sorted array and similar) was passed 10/10 by both models and did not separate them.

This is one sample of 60 Python tasks, not the full HumanEval set, and it does not
measure JavaScript, TypeScript or SQL, debugging or refactoring.

## 256K context on q2_0

The serving profile was used unchanged: `--max-context 262144`, `--kv q4_0`,
`--kv-resident 32768`, the control vector and the conversation cache. The
needle-in-a-haystack check in `tools/needle_bench.py` put one code word into a long
text and asked for it back.

| Prompt tokens | Depth | Result | Time |
| ---: | ---: | --- | ---: |
| 31,748 | 50% | found | 39 s |
| 122,324 | 50% | found | 126 s |
| 255,387 | 10% | found | 276 s |
| 255,387 | 50% | found | 273 s |
| 255,387 | 90% | found | 277 s |

At 255,387 tokens the server reported 49.5 to 82.0 tok/s output over the nine-token
answers, with a first answer after about 4.6 minutes. The 256K window is accepted and
the fact was recovered at the beginning, middle and end of it.

## Long-context coding

One small function (`windowed_stats`: min, max and mean of every contiguous window)
was placed inside a long project-like text at 10%, 50% or 90% depth. The model was
asked to find the single task block and return only the function. The hidden checks
covered normal input, one element, an empty list, negative numbers, a window of 0, a
window of -1 and a window longer than the list.

| Prompt tokens | Depth | Result | Wall time | Prefill | Output |
| ---: | ---: | --- | ---: | ---: | ---: |
| 30,279 | 50% | pass | 42.6 s | 936 tok/s | 63.0 tok/s |
| 120,255 | 50% | pass | 153.6 s | 934 tok/s | 31.7 tok/s |
| 250,253 | 10% | pass | 276.5 s | 881 tok/s | 63.4 tok/s |
| 250,253 | 50% | pass | 277.3 s | 878 tok/s | 63.4 tok/s |
| 250,253 | 90% | pass | 279.7 s | 883 tok/s | 57.2 tok/s |

The 250K prompts were counted at 250,253 tokens; the engine reported 233,869 prompt
tokens read because 16,384 tokens were cached from the previous 256K test. All five
answers passed the hidden checks. The first 256K answer took about 4.6 minutes to
start; output then ran at 57 to 63 tok/s. This tests retrieval, instruction following
and code generation in a 256K window, not a whole-repository refactor.

## Decision

- Gyro-S is not faster on this PC. It saves about 7.6 GiB of loaded weights, but it
  decoded 13 to 26% slower and its coding result was one task better out of 60 while
  taking 1.7x longer.
- q2_0 stays the coding model. At 256K it stayed up, read 255,387 tokens, answered,
  recovered a fact at 10%, 50% and 90% depth, and passed all five long-context coding
  checks (30K, 120K and 250K, including 10/50/90% depth).
- The Gyro-S file and pack were deleted after the run; the raw result files stayed in
  `.orca/` for this PC.

## The helper fix

`native_expert_parity --load-check` crashed with `0xC0000005` on the Gyro-S pack:
it called `ggml_type_name()` for the trellis ids 145/146, which are above
`GGML_TYPE_COUNT`. It now prints `TQK6`/`TQK7` through `type_label()`, reports a
missing GGUF without dereferencing a null tensor, and stops cleanly on an empty
layout. The Gyro-S load check then ended with `0 failures`, exit 0.
